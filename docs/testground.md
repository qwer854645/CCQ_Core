# CCQ 工程试验场 · 已合并至 CCQ Core 0.4.88

Minecraft 1.21.1 / NeoForge 21.1.247+ / Create 6.0.10+，Java 21。

本功能已内置于 `ccq_core` 0.4.88。升级时同时移除独立的 `ccq_testground` JAR。维度、方块、传送门配对和玩家计时数据的键名保持不变。客户端和服务器均需升级。

## 怎么测试

1. 将 `ccq_core-0.4.88.jar` 放入实际游戏目录的 `mods` 文件夹，并移除旧核心模组及独立试验场 JAR，重启游戏。原测试存档可继续使用；地形改动只作用于新生成区块。
2. 用 Create 的**工业铁块**（`create:industrial_iron_block`）搭竖直矩形门框。
3. 最小门洞为 **宽 2、高 3**，含框架外尺寸为 **4×5**，四角也使用工业铁块，共 14 块；支持门洞宽 2–21、高 3–21。
4. 手持 Create 扳手，右键门框朝向门洞的内侧面。例如右键底边上表面。门洞会出现淡蓝色网格。
5. 创造模式接触门面立即传送；生存模式走入门面并等待原版下界门游戏规则指定的时长（默认约 **4 秒**），首次使用会在另一侧自动建立对应门和落脚平台。
6. 走出出口，等待原版冷却结束后可再进入返回。停留在出口内不会立刻反复传送。

```text
工业铁块 工业铁块 工业铁块 工业铁块
工业铁块   门洞     门洞   工业铁块
工业铁块   门洞     门洞   工业铁块
工业铁块   门洞     门洞   工业铁块
工业铁块 工业铁块 工业铁块 工业铁块
```

横向沿 X 或 Z 建门均可。黄铜机壳等可以装饰门外，但首版要求实际门框完整使用工业铁块。

## 已实现

- 维度 ID：`ccq_testground:testing_ground`。
- 地表基准约 Y=128，以同高平地为主，穿插更广泛的大尺度缓坡丘陵（固定测试种子采样约 67% 为同高平地），地下从 Y=-64 起，建筑上限沿用 Y=319。
- 表层为 5 格厚安山岩，不铺草方块或泥土；地底有石头、深板岩、底层基岩；关闭洞穴雕刻、含水层和洞穴噪声，不铺设地下湖或熔岩湖。
- 原版主世界矿石，以及安装对应模组时的锌、铅、铀、钍、硝酸盐、铂和盐。使用测试维度专用的高密度矿团与高度配置，不改变其他维度。
- 关闭区块生成时的生物生成，并清空动物、蝙蝠及水生动物的自然生成列表；已有动物和手动带入的动物保留，怪物自然生成列表保留。
- 不生成树木或草丛，天空固定正午，群系不降雨。
- 稀疏生成一座完整的原创工程基地（120×300×30，宽×长×模板高度），替代原来三种独立设施的自然生成。基地包含机械勘测站、加长火炮试射场、机械检修工坊、双层值班宿舍、仓库、装卸场、道路、露天吊运装配区、停车检修棚、材料堆场、供水站和后勤用房，可自由拆建。宿舍有四张床、厨房、餐桌、值班区和阳台。
- 勘测站保留静态观测仪，使用有操作通道的器材绞车吊运箱子，移除未完整装配的观测台传动。
- 炮场三条靶道分别到达纵向 80、140、200 格位置。青铜、铸铁和钢炮使用两节药室及适合材质的炮管长度，炮体位于正常炮架上方两格，并保存炮段连接数据。转速控制器配合一个大齿轮提供手摇动力，预设输出 1 RPM，两个离合器可分别切断俯仰和回转支路；炮架背面拉杆用于装配。控制器、手摇柄与离合器均可从地面操作。
- 工坊改用固定桥架、共轴双绳索滑轮与一体吊梁，使用 Create 原生镜像同步，保留检修沟、齿轮台与冲压台。生成时所有曲柄和装配拉杆均未启动，炮内没有预装弹药。
- 原三处设施各保留一个主题补给箱，首次打开随机抽取 8–12 组物资，常规材料每组约 8–24 件。勘测站提供食物、火把与基础材料；炮场提供金属、火药、木炭与红石；工坊提供合金、轴、齿轮、金属板和电子管。扳手等工具仍按单件抽取。
- 勘测站和炮场各有 1 个补给木桶，工坊有 4 个，首次打开生成 4–7 组主题补给，常规材料每组约 4–12 件；其余工坊木桶及吊运箱子保留空置。补给木桶另有独立 20% 概率额外获得精密构件、钻石或坚固板。
- 设施补给箱有独立 65% 概率的稀有奖励：精密构件、钻石、坚固板、下界合金碎片，或工坊专属的转速控制器、机械手、机械臂等。另有独立 6% 概率额外获得一个下界合金锭或附魔金苹果。两档抽取相互独立，均不会替代基础补给，重复打开不会重抽。
- Create Big Cannons 5.11.7+ 为必需依赖，炮场统一使用完整火炮模板。
- 仓库的五组货架分为建材、金属、传动、装配控制、火炮，40 个木桶全部写入固定分类库存，另有 1 个公用工具箱，合计 114 种、3,787 件物品。容器使用默认名称，不放置分类标牌；物品仍按货架位置固定分类。库存直接保存在模板物品 NBT 中，不使用随机战利品表。

- 休息区有 5 个随机补给容器：餐厨食物储备、医疗应急箱、两处卧室储物箱和衣物杂物桶。包含熟食、面包、蜂蜜、牛奶、书纸、羊毛、蜡烛、工具等生活用品；医疗箱保证生成治疗、再生药水和金苹果。
- 基地原有预留地块已布置为生活小院、三车位停车棚、装填准备棚、带冲压台的检修棚、轨道装卸区、同步吊运装配区、材料堆场、供水站及后勤/观察用房。窄地块补充备料架、托盘和连接步道；道路与原三条炮场射线保留，靶场末端新增阶梯挡弹墙。
- 围墙沿四周补齐为连续石砖墙基与铁栏，保留前后两个出入口，主路贯通；新增区域继续不使用容器自定义名称和标识牌。
- 新增七处补给，包含餐厨、装填、装卸、材料、供水与值班物资。全基地共 21 个随机补给容器和 41 个固定库存容器；上述物品在新生成基地生效。旧箱内物品不会重置；旧仓库的现有木桶不会自动改写库存，`repairbase` 仅补齐空气位置。
- 基地的数据默认采用 64 区块间距、32 区块分离的随机网格（受 Structurify 间距倍率影响；ser 的 1.25 倍率对应 80/40 区块），只接受完整占地范围采样高差不超过 2 格的位置，随机旋转，底部最多补 3 格安山岩。内部按三个 120×100 区段生成，共用朝向、地面高度和地形判定，避免 300 格长结构超出原版区块引用范围而缺损。
- 不干预爆炸、物品、背包、游戏模式、机器运转和 FTB 领地设置。
- X/Z 按 1:1 寻找出口，Y 按目标地面确定。若对应位置有建筑，会在附近 32 格内寻找空地，找不到则取消传送并提示。
- 每对门固定配对，记录保存在存档的 `data/ccq_testground_portals.dat`。重新进入存档仍保留。
- 拆除框架会使门面失效；在原位置重建相同门框时可继续利用原配对。
- 支持玩家与普通实体；骑乘中的实体及带乘客的载具不触发本模组传送，不负责搬运 Create 移动结构、火炮结构或 Sable 飞行器。

## Create 列车

工程传送门已接入 Create 6.0.10 的原生 `PortalTrackProvider` 接口。

- 先激活门，再将平直轨道垂直朝向门面铺到紧邻门面的一格；不要用轨道替换门面方块。
- Create 会把这段轨道转成传送门轨道，并在配对门的对应位置生成、绑定另一端轨道。之后从出口接着铺轨。
- 入口与自动出口的门洞尺寸一致；轨道在门洞内的横向列与高度偏移保持对应。
- 列车由 Create 的跨维度轨道与车厢系统处理，不走普通实体直接传送。
- 按实际车体宽高搭建足够大的门洞。若配对出口原来是小门，可先手动扩建出口框架再连接轨道。
- 自动测试已验证轨道双向绑定与拆门失效；整列车驾驶、载客、时刻表和长编组仍需实际试车。

## 合并与验证

代码位于 `src/main/java/ccq/core/testground`，由 `CcqCoreMod` 调用 `TestGroundModule.register`。资源保留在 `data/ccq_testground` 与 `assets/ccq_testground`，仅保留命名空间，不再声明独立模组。

配对文件仍为存档 `data/ccq_testground_portals.dat`，实体计时与冷却由 Minecraft 原版 `PortalProcessor` 管理，旧 `ccq_testground_travel` 状态不再使用。

十六项 GameTest 位于 `src/testgroundSmoke`；测试专用结构模板与世界预设不进入成品 JAR。工程设施模板属于正式资源，会打入成品。机械测试在独立批次中检查四种旋转方向的接口、实际动力传递、吊运与火炮装配和试射；基地测试检查正负坐标生成、共享设置不被修改，以及整区块恢复后保留已有方块与箱内物品，同时核对炮场四角柱完整、无容器命名和标识牌。兼容测试依赖目录包含 ser 同版本 C2ME、Structurify、Structure Layout Optimizer 及 Resourceful Config，Structurify 配置复制自 ser（防重叠开启，间距倍率 1.25）。测试另行检查原版沙漠神殿仍受防重叠检查约束。生活区专项测试核验实际家具连接、支撑和玩家碰撞路径，并用厨房炉灶和汤锅实际烹饪炖牛肉。场地专项测试检查围墙连续、主路和后门可通行，验证新增双吊点吊机抬升整根吊梁、检修棚冲压台获得动力，搅拌机实际旋转，以及水泵把水从蓄水池送入一格高接水池。四种朝向分别检查栏杆、家具、楼梯等相邻连接状态，并使用原版光照传播核验厂区铺地完整、棚下可站立地面方块光照至少为 8。内饰测试依赖目录为 `.dev-testground-mods/.dev-interior`，包含上述家具模组及 Moonlight。

场地扩展布局位于 `tools/expand_engineering_base_yards.py`，以 `tools/engineering/base_before_yards_084.nbt` 为可重复生成的基底。完整重建顺序：场地脚本 → 补给脚本 → 宿舍内饰脚本，每一步都会同步生成区段。

合并基地的完整模板为 `src/main/resources/data/ccq_testground/structure/engineering/engineering_base.nbt`；执行 `py -3 tools/split_engineering_base.py` 可重新导出自然生成使用的三个区段（需要 nbtlib）。仓库固定物品与休息区补给定义在 `tools/update_engineering_base_supplies.py`，执行该脚本会重新写入完整模板的补给，并同步导出三个生成区段。容器不写入自定义名称或标识牌；收尾规则位于 `tools/engineering_template_cleanup.py`。生活区布局位于 `tools/furnish_engineering_lodge.py`，需要重导出时先运行补给脚本，再运行内饰脚本；内饰脚本同时导出完整基地、三个区段和可单独放置的 `engineering/duty_lodge` 模板。旧机械布局源文件与 `tools/generate_engineering_structures.py` 保留用于维护旧设施模板。旧结构注册与模板仅用于旧存档读取和手动放置，已停用自然生成。

炮场操作：背面拉杆用于装配，炮架侧面地面处设有手摇柄与转速控制器；两个离合拉杆分别控制俯仰和回转支路，通电时断开对应支路。试射测试使用一发实心弹与一个 4 档大号定装药筒，保留 CBC 原生故障机制。生成时不预装这些弹药，具体装填步骤沿用 CBC 思索教程。

工坊吊机：爬上侧面的梯子，在上方曲柄处驱动双滑轮，反向操作可改变升降方向。两个吊点连接同一根线性机箱吊梁，使用原生父子滑轮同步；勘测站绞车曲柄可从中层通道接近。

## 查找工程设施

升级后只有新生成区块会采用新版基地与内饰；已生成的旧设施和旧家具保留，不会自动替换。`repairbase` 只补空气位置，不负责将旧家具重布置为新布局。可在试验场内使用：

```mcfunction
/locate structure ccq_testground:engineering_base
/locate structure ccq_testground:engineering_base_ruined
```

管理员可在足够大的空旷区域，用一次指令放置整座完整基地或损坏基地。指令不受自然生成网格、平整度或生物群系限制，按指定位置放置，会覆盖模板记录位置的方块。完整基地为 120×30×300；损坏基地为 120×42×300，其中 12 格属于地下。两者的指令坐标都表示原平台基底，损坏版自动向下偏移 12 格，无需手动减 Y。

```mcfunction
/place structure ccq_testground:engineering_base
/place structure ccq_testground:engineering_base_ruined
/place template ccq_testground:engineering/engineering_base
/place template ccq_testground:engineering/engineering_base_ruined
/place template ccq_testground:engineering/duty_lodge
```

## 修复 0.4.79 已生成的残缺基地

0.4.80 修复了并行生成时多个区块共享放置范围的竞争问题；0.4.81 进一步修复 Structurify 将基地三个相邻区段视作冲突结构、只保留部分区段的问题。基地在其专属维度中豁免这项防重叠检查，其他结构的规则、Structurify 全局配置与间距倍率保留。已保存的区块不会自动重新生成。

站在残缺基地范围内，使用管理员命令：

```mcfunction
/ccqtest repairbase
```

命令读取附近实际保存的结构起点，补齐整座基地中模板位置当前为空气的方块，保留所有现有非空气方块、箱内物品及已有战利品抽取状态。命令也会恢复基地范围内后来主动拆成空气的模板方块，因此请只在需要补齐基地时执行。不会自动运行，不会清空区块或重置整个维度。重复执行不会重复抽取已有箱子的战利品。

构建：`gradlew.bat build --offline`。

使用独立的本地依赖目录运行集成测试：`gradlew.bat runTestgroundSmoke -Pdev_modpack_mods_dir=.no-dev-runtime -PtestgroundSmokeMods=<依赖目录> --offline`。测试数据写入 `run-testground-smoke`。

## 连接状态和照明维护（0.4.86）

地基顶层与周边地表对齐，厂区内部补齐连续铺地，前后入口使用过渡台阶。检修棚改为地面冲压、搅拌和工具准备工位，取水输出池仅一格高。

`tools/engineering/connection_states.json` 保存原生模组邻接计算得到的四朝向状态及补灯位置；分段脚本同时导出三个区段的四种朝向，共十二个资源。生存生成按实际朝向选用对应资源，避免家具旋转后连接属性不随朝向转换的问题。脚本重建时自动应用这些数据。修改布局后，先用独立依赖运行 `runTestgroundSmoke -PengineeringStateBake=true` 重新烘焙，再执行 `py -3 tools/split_engineering_base.py` 导出模板。原生烘焙工具在 `tools/native`，只在显式传入该属性时编译，不进入成品。
